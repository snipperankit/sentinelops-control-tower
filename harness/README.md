# Harness (harness/)

## Purpose

TrueForge integration: sessions, events, and approval-resume handling (see ARCHITECTURE.md). Also hosts the local health check and the deterministic demo-world scripts used for the hackathon demo.

## Scope

Runtime wiring between TrueForge and SentinelOps domain code, plus `harness/demo/` (the deterministic demo-world domain model, store, read-only queries, health check, and CLI scripts), `harness/healthcheck.ts`, `harness/agent/` (the TrueForge session/agent integration layer), and `harness/audit/` (the evidence-provenance store, incident evidence graph, and tamper-evident audit chain).

### `harness/agent/`

- `client.ts` — `createTrueForgeClient(env)`, a thin factory reading `TRUEFORGE_BASE_URL` and optional `TRUEFORGE_TOKEN`.
- `result-schema.ts` — `investigationResultSchema` (zod) and a hand-authored, manually-synced `investigationResultJsonSchema` JSON Schema literal used as the commander agent's `responseFormat`.
- `spec.ts` — `buildCommanderAgentSpec()` builds the versioned commander `AgentSpec`: model from env, the `agents/commander/system-prompt.v1.md` instructions (loaded by the caller), exactly three MCP connectors (observability, deployments, incidents) each hard-restricted to `enableTools: ["@read-only"]`, the `incident-investigation` skill, a bounded `iterationLimit` (default 25), and the structured response format. No rollback-capable connector is ever attached — this repo has no policy gateway yet, so rollback stays disconnected in this phase rather than merely gated.
- `events.ts` — `SessionEventStore` interface + `InMemorySessionEventStore`; `extractToolProvenance()` recovers each MCP tool's `.provenance` envelope from `tool.response` event content.
- `session.ts` — `AgentSessionRunner`, built against a narrow `TrueForgeClientLike` interface (not the concrete SDK class) for testability: `startInvestigation()` creates a session and streams the first turn; `resumeInvestigation()` calls `getTurn` and either returns a terminal state directly or resumes a running turn via `subscribeToTurn({ afterSequenceNumber })` from the last locally-recorded sequence id. Streaming `*.delta` events are never persisted (the authoritative final message is `turn.done.state.output`); every other event is appended to the event store with its tool provenance, if any.
- `specialist-result-schema.ts` — `SPECIALIST_NAMES`/`SpecialistName`, `specialistVerdictSchema`/`SpecialistVerdict` (`"supports_mutation" | "against_mutation" | "inconclusive"`), and one zod schema + hand-authored JSON Schema pair per specialist (`observabilityFindingsSchema`, `deploymentFindingsSchema`, `runbookFindingsSchema`, `securityReviewFindingsSchema`, `verificationFindingsSchema`), each extending a common `summary`/`toolsUsed`/`verdict`/`reason` base. `toolsUsed` is self-reported by the specialist and independently cross-checked by `delegation.ts` — never trusted on its own.
- `specialists.ts` — one `build*AgentSpec()` function per specialist (observability investigator, deployment investigator, runbook investigator, security reviewer, verification agent). Each attaches an explicit literal `enableTools` array (never `@all`/`@read-only`/other wildcard selectors) via `buildRestrictedMcpServer()`, its own skill, its own typed `responseFormat`, and a shared `buildSpecialistConfig()` that deliberately omits `dynamicSubAgents` — structurally, no specialist spec can start a further sub-agent. The security reviewer gets `mcpServers: []` (it has no tool at all); the verification agent gets two connectors each narrower than the corresponding investigator's.
- `delegation.ts` — bounded, deterministic delegation enforcement independent of prompt wording. `DelegationTracker` (`DEFAULT_DELEGATION_LIMITS = { maxDepth: 1, maxDelegations: 5 }`) tracks the active delegation chain and total count, throwing `DelegationDepthExceededError`, `DelegationBudgetExceededError`, or `DelegationLoopDetectedError` (same specialist already active in the chain) from `beginDelegation()`; the returned `DelegationScope.end()` is idempotent and released in a `finally`. `DelegationCoordinator.delegate()` wraps a tracker reservation around a specialist invocation (`options.run()`) and independently cross-checks the specialist's self-reported `toolsUsed` against `options.allowedTools`, throwing `UnauthorizedToolAccessError` otherwise — mirroring `policy/gateway.ts`'s fail-closed, independently-checked authorization pattern.
- `disagreement.ts` — `detectDisagreement(entries)`, a pure O(n²) pairwise comparison of specialist verdicts; returns a `DisagreementEntry` for every pair whose verdicts differ, preserving both specialists' verdicts and reasons.
- `aggregate.ts` — `aggregateSpecialistFindings(findings)` combines specialist results into a `MultiSpecialistReport` whose `disagreements` field (from `disagreement.ts`) is always present (empty array when specialists agree, never omitted/undefined) alongside every specialist's full findings and a `hasDisagreement` flag — the structural guarantee behind "the commander must not hide conflicting results."
- `prompt-injection-scan.ts` — `scanForPromptInjection(text)`, an 11-pattern case-insensitive heuristic scanner (e.g. "ignore ... instructions", "skip ... approval", "roll ?back immediately", "you are now", "approved automatically") used by the security reviewer specialist to flag suspicious tool-output/runbook content; a heuristic defense-in-depth layer, not a replacement for treating all tool output as untrusted.

### `harness/audit/`

- `evidence.ts` — `EvidenceStore`: `record(input)` validates provenance (`sessionId`, `sourceTool`, `query`, `trust: "trusted" | "untrusted"`, `interpretation`, `result`) via zod, rejecting anything incomplete with `MissingEvidenceProvenanceError` rather than recording a partial item; redacts sensitive fields in `result` (`redaction.ts`) before ever hashing or storing it; assigns a fresh `randomUUID()` id and a `resultHash` (SHA-256 over canonical JSON, `hash.ts`). `verifyEvidenceIntegrity(item)` recomputes the hash and compares — the mechanism behind "modified evidence detection". `replay(id)` returns the stored item plus a live integrity check, making evidence replayable. The class has no update or delete method: evidence, once recorded, cannot be rewritten or removed — a structural guarantee, not a prompt instruction (AGENTS.md non-negotiable).
- `graph.ts` — `EvidenceGraph` links evidence to hypotheses (`recordHypothesis`, validating every `supportingEvidenceIds` entry exists, else `UnknownEvidenceReferenceError`), hypotheses to proposed actions (`recordProposedAction`, validating `supportingHypothesisIds`, else `UnknownHypothesisReferenceError`), and approval requests to evidence (`linkApprovalRequest`/`getEvidenceForApproval`, referencing the policy layer only by an opaque `approvalRequestId` string — `harness/` never imports `policy/` types, keeping the layers decoupled per AGENTS.md). Ruled-out hypotheses (`ruledOut: true`, with a `reason`) are recorded, never deleted, so alternative hypotheses are always preserved and visible via `listHypotheses()`.
- `chain.ts` — `AuditChain`: `append(input)` redacts the payload, links it to the previous entry's hash (`GENESIS_HASH` for the first entry), computes a SHA-256 hash over the entry's own fields, and appends it; there is no update or delete method, so the chain is append-only. `verifyChainIntegrity()` recomputes every entry's hash and cross-checks each `previousHash` link, returning `{ valid: false, brokenAtSequence }` at the first entry whose stored hash or link no longer matches what its (possibly tampered) fields recompute to.
- `versions.ts` — `buildVersionManifest(input)` validates all eight required version components (`agentVersion`, `modelVersion`, `policyVersion`, `toolVersion`, `sandboxVersion`, `approvalVersion`, `mutationVersion`, `verificationVersion`) are present and non-empty, throwing `MissingVersionComponentError` otherwise. Callers record the manifest onto an `AuditChain` as a normal event (e.g. `chain.append({ type: "session.versions_recorded", sessionId, payload: manifest })`) rather than `AuditChain` having a dedicated method for it.
- `redaction.ts` — `redactSensitiveFields(value)`, a pure, recursive, non-mutating redactor matching field names (case-insensitive) against a fixed list of sensitive patterns (API keys, tokens, passwords, secrets, authorization headers, CVV/card/account numbers, SSNs) per SECURITY.md "Audit security"; used by both `evidence.ts` (before storing a result) and `chain.ts` (before storing/hashing a payload).
- `hash.ts` — `stableStringify` (recursive key-sorted JSON serialization) and `sha256`, intentionally duplicating (not importing) `policy/approval.ts`'s canonicalization pattern to keep `harness/` and `policy/` decoupled; `deepCloneJson` for defensive copies.
- `errors.ts` — typed error hierarchy (`AuditError` base; `MissingEvidenceProvenanceError`, `UnknownEvidenceReferenceError`, `UnknownHypothesisReferenceError`, `MissingVersionComponentError`) mirroring `policy/errors.ts`'s pattern.

### `agents/commander/` and `agents/skills/incident-investigation/`

`agents/commander/system-prompt.v1.md` is the versioned commander system prompt (establish scope → read-only investigation → deployment inspection → runbook retrieval → evidence/alternative-hypothesis synthesis → stop before proposing a mutation if evidence is insufficient; treats all tool output as untrusted). `agents/skills/incident-investigation/SKILL.md` is the paired investigation procedure. Neither file can authorize a mutation — that boundary is enforced structurally in `spec.ts`, not by prompt wording alone.

The demo world models the PRODUCT_SPEC.md payment-failure scenario: deployments `4c18`-`4c20` are healthy, `4c21` reduces the checkout timeout and causes a regression, and a `rollbackTo()` state transition restores a prior deployment and appends recovery metrics. State is a single deterministic JSON document (`.demo-state/world.json`) written by `DemoWorldStore`; no SQL engine is used yet.

## Assumptions

Demo fixtures are static, checked-in JSON under `harness/demo/fixtures/` (`world.json` seed state, `recovery-metrics.json` post-rollback metrics); no external services are required to seed or check the demo world. Timestamps are either fixed fixture values or produced by an injectable `Clock` (`SystemClock` at runtime, `FixedClock` in tests).

## Security implications

Must never inject production credentials into agent or sandbox context. The demo world contains only synthetic, non-sensitive data.

## Failure behavior

`healthcheck.ts` and `demo/*.ts` exit non-zero on any failed check so CI and local runs fail loudly instead of silently. `DemoWorldStore` throws typed errors (`WorldNotSeededError`, `UnknownDeploymentError`, `InvalidRollbackTargetError`) rather than returning ambiguous values, and `rollbackTo()` rejects unknown or already-active/rolled-back targets.

## Test or eval coverage

`tests/unit/demo-world.test.ts` covers the unseeded, healthy/faulty-seeded, rolled-back, and reset states, the read-only query API, and `checkWorldHealth()` across those states, using a `FixedClock` and a temporary state file for determinism and isolation. `tests/unit/agent-spec.test.ts` covers the commander spec's read-only-only connector list, bounded iteration limit, skill/sandbox wiring, and response format. `tests/unit/agent-session.test.ts` covers `AgentSessionRunner` event-store/provenance persistence and both resume branches (terminal vs. running), using fake `TrueForgeClientLike` implementations — no live TrueForge server is required or used. `tests/unit/specialist-specs.test.ts` covers each specialist's distinct/explicit tool allowlist and the absence of `dynamicSubAgents`. `tests/unit/delegation.test.ts` covers depth limits, budget limits, delegation-loop detection, and unauthorized-tool-access rejection (with tracker-slot release verified in all cases). `tests/unit/disagreement.test.ts` and `tests/unit/aggregate.test.ts` cover pairwise disagreement detection and its guaranteed presence in the aggregated report. `tests/unit/prompt-injection-scan.test.ts` covers the security reviewer's scanner against synthetic phrasing and the real `mcp/incidents/runbook-catalog.ts` injection fixture. `tests/unit/evidence.test.ts` covers evidence ID uniqueness, untrusted-source labeling, missing-provenance rejection, redaction on record, modified-evidence detection, and replay. `tests/unit/evidence-graph.test.ts` covers evidence-to-hypothesis, hypothesis-to-action, and approval-to-evidence linkage (including rejection of unknown IDs) and preservation of ruled-out alternative hypotheses. `tests/unit/redaction.test.ts` covers sensitive-field matching, nested redaction, and non-mutation of the input. `tests/unit/audit-chain.test.ts` covers hash-chain linkage from genesis, payload redaction, and tamper detection (both a modified payload and a rewritten `previousHash` link). `tests/unit/version-manifest.test.ts` covers a complete manifest and rejection of manifests missing any required version component.

## Known limitations

`harness/agent/` has not been validated against a live TrueForge server — only against fake `TrueForgeClientLike` implementations in unit tests. The demo world is file-based (no SQL engine) and single-incident (one scenario, one rollback target). Bounded specialist delegation (`delegation.ts`) is a real, independently-enforced TypeScript mechanism, not prompt-only — but there is no orchestration code yet that wires the commander to actually invoke `DelegationCoordinator` against a live specialist TrueForge session; `run()` is exercised so far only with fakes in `tests/unit/delegation.test.ts`, pending a future commander-orchestration layer.

`harness/server/` (see its own README) now wires `harness/audit/` (`EvidenceStore`, `EvidenceGraph`, `AuditChain`) into a real, non-scripted incident session: real MCP tool calls, a real sandboxed diagnostic, the real policy gateway, the real rollback mutation, and real post-rollback verification, exposed to the cockpit over HTTP + SSE. What remains simulated: the investigation narrative in that session is not yet driven by a live TrueForge LLM turn loop (`AgentSessionRunner`/`harness/agent/session.ts`) — specialist findings there are synthesized directly from the real tool evidence, not from independent live TrueForge specialist sessions. Wiring `AgentSessionRunner` into `LiveIncidentSession.runInvestigation()` is the natural next step once a reachable `TRUEFORGE_BASE_URL` is confirmed.
